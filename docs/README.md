## Documentation maintenance

- Use standard relative Markdown link destinations, not machine-specific absolute paths or Obsidian-only wikilinks. These links work in Obsidian and remain portable in GitHub and other Markdown viewers.
- Link to canonical documents and relevant implementation directories/files rather than copying their content into this map.
- When adding or materially changing a module, implementation area, capability, or module document, update the relevant subsystem entry with its canonical documentation, implementation path, current capability, and related archive. Add every new current capability and every completed change after it is archived.
- When changing a capability or its implementation, update the corresponding capability's related-documentation references when useful; preserve normative requirements and historical archive content.
- Check new or changed relative links from the Markdown file's own directory and link only to files or directories that exist.
- Run `python scripts/check_documentation_map.py` before submitting; CI runs the same check on every pull request.
- The validator is [`scripts/check_documentation_map.py`](../scripts/check_documentation_map.py), and its required pull-request check is defined in [Documentation Integrity CI](../.github/workflows/documentation.yml).
- The `main` branch protection rules require the GitHub status check `Check documentation links and map coverage` before merging.
